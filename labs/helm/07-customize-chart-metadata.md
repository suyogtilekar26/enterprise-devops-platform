# Helm Lab 07 - Customize Chart Metadata

# Enterprise DevOps Platform

---

# Lab Objective

In this lab, we will customize the metadata of the API Gateway Helm Chart.

The default metadata generated by `helm create` is only a placeholder.

Every production Helm Chart should contain meaningful metadata so that engineers can easily identify:

- Application
- Version
- Maintainer
- Description
- Kubernetes Compatibility

This metadata is stored in the `Chart.yaml` file.

---

# Production Scenario

Company

ABC Bank

The Platform Team manages more than 500 Helm Charts.

Every chart follows a standard metadata format.

Example

- Chart Name
- Description
- Version
- Application Version
- Maintainer
- Source Repository

This enables GitOps platforms such as Argo CD and ArtifactHub to display useful information about deployed applications.

We will implement the same standard.

Open the Chart.yaml file.


# Step 2

Replace the generated content with the following.

```yaml

```

---

# Understanding Each Field

---

## apiVersion

```yaml
apiVersion: v2
```

Defines the Helm Chart specification.

Modern Helm Charts use:

```
v2
```

---

## name

```yaml
name: api-gateway
```

Unique chart name.

Usually matches the application name.

---

## description

```yaml
description: API Gateway Helm Chart for Enterprise DevOps Platform
```

Human-readable explanation.

Useful when multiple charts exist.

---

## type

```yaml
type: application
```

Two common values:

```
application

library
```

Our chart deploys an application.

---

## version

```yaml
version: 1.0.0
```

Chart Version.

Incremented whenever the Helm Chart changes.

Example

```
1.0.0

↓

1.0.1

↓

1.1.0
```

---

## appVersion

```yaml
appVersion: "1.0.0"
```

Represents the application version.

Example

```
Docker Image

api-gateway:v1.0.0
```

Changing the application version does not always require changing the chart version, although many teams update both together during releases.

# Production Best Practices

- Use semantic versioning for chart versions.
- Keep chart names consistent with application names.
- Write meaningful descriptions.
- Track application version separately from chart version.
- Validate every metadata change using `helm lint`.

---

# Common Mistakes

- Confusing `version` with `appVersion`.
- Using generic descriptions.
- Skipping chart validation.
- Using inconsistent naming conventions.
- Forgetting to update chart version after structural changes.

---

# Interview Questions

## Q1. What is the difference between `version` and `appVersion`?

### Answer

`version` represents the Helm Chart version.

`appVersion` represents the version of the application being deployed.

---

## Q2. Why is `Chart.yaml` important?

### Answer

It defines the chart metadata required by Helm, including the chart name, description, version, type and application version. Helm uses this information during packaging, validation and deployment.

---

## Q3. Why should engineers run `helm lint` after modifying `Chart.yaml`?

### Answer

`helm lint` validates the chart structure and metadata, helping detect syntax or configuration issues before deployment.
