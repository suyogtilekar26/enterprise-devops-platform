# Helm Lab 08 - Customize values.yaml for API Gateway

# Enterprise DevOps Platform

---

# Lab Objective

In this lab, we will customize the `values.yaml` file for our API Gateway Helm Chart.

Instead of using the default values generated by Helm, we will configure values specific to our Enterprise DevOps Platform.

This approach allows us to deploy the same Helm Chart across:

- Development
- QA
- UAT
- Production

without modifying Kubernetes templates.

---

# Production Scenario

Company

ABC Bank

The API Gateway is deployed in four environments.

Only configuration changes between environments.

Example

Development

- 1 Replica
- Small CPU
- Development Image

Production

- 5 Replicas
- High CPU
- Production Image

The Deployment template remains identical.

Only `values.yaml` changes.

This is a fundamental Helm design principle.

# Step 1

Open the values file.

```bash
nano helm/charts/api-gateway/values.yaml
```

---

# Step 2

Replace the generated content with the following.

```yaml
replicaCount: 2

image:
  repository: enterprise-devops-platform/api-gateway
  pullPolicy: IfNotPresent
  tag: "1.0.0"

service:
  type: ClusterIP
  port: 5000

ingress:
  enabled: false

resources:
  requests:
    cpu: 100m
    memory: 128Mi

  limits:
    cpu: 500m
    memory: 512Mi

autoscaling:
  enabled: false

serviceAccount:
  create: true

nodeSelector: {}

tolerations: []

affinity: {}
```

# Understanding Each Section

---

## replicaCount

```yaml
replicaCount: 2
```

Defines how many Pods should run.

Example

```
API Gateway

↓

2 Pods
```

Production may use:

```
5

10

20
```

depending on traffic.

---

## image

```yaml
image:
```

Defines

- Docker Image
- Image Tag
- Pull Policy

Example

```
enterprise-devops-platform/api-gateway:1.0.0
```

Future CI/CD pipelines will automatically update the image tag.

---

## service

```yaml
service:
```

Defines the Kubernetes Service.

Example

```
Type

ClusterIP

Port

5000
```

The API Gateway will receive traffic internally from the Frontend.

---

## ingress

```yaml
enabled: false
```

Ingress is disabled for now.

A dedicated Ingress will be configured in later labs.

---

## resources

Defines CPU and Memory requirements.

Requests

```
Guaranteed Resources
```

Limits

```
Maximum Resources
```

Example

```
Request

100m CPU

128Mi RAM

Limit

500m CPU

512Mi RAM
```

---

## autoscaling

Currently disabled.

Later labs will enable HPA.

Example

```
CPU > 70%

↓

Scale Pods Automatically
```

---

## serviceAccount

```yaml
create: true
```

A ServiceAccount will be created automatically.

This is recommended for production workloads.

---

## nodeSelector

Used to schedule workloads on specific nodes.

Currently empty.

---

## tolerations

Used when deploying onto tainted nodes.

Currently empty.

---

## affinity

Used for advanced Pod scheduling.

Currently empty.

# Production Best Practices

- Never hardcode values inside templates.
- Keep environment-specific values outside the chart when possible.
- Store secrets separately from values.yaml.
- Use semantic image tags.
- Define CPU and Memory requests for every production workload.
- Maintain separate values files for each environment.

---

# Common Mistakes

- Hardcoding image tags in templates.
- Omitting resource requests.
- Using the `latest` Docker tag.
- Mixing production and development values.
- Storing passwords inside values.yaml.
- Ignoring Helm validation after changes.

# Interview Questions

## Q1. Why is values.yaml important?

### Answer

`values.yaml` stores configurable parameters that are injected into Helm templates, allowing the same chart to be reused across multiple environments without modifying template files.

---

## Q2. Why should image tags be stored in values.yaml?

### Answer

Image tags change frequently during deployments. Keeping them in `values.yaml` allows CI/CD pipelines to deploy new versions without modifying Kubernetes templates.

---

## Q3. Why define CPU and Memory requests?

### Answer

Requests help the Kubernetes Scheduler place Pods correctly, while limits prevent applications from consuming excessive cluster resources.
