# Helm Lab 04 - Understand the Generated Helm Chart

# Enterprise DevOps Platform

---

# Lab Objective

The goal of this lab is to understand every file generated by the `helm create` command.

Enterprise DevOps Engineers should never blindly modify Helm Charts.

Before customizing a chart, engineers must understand:

- What every file does
- Why Helm generated it
- Whether it is required
- How it fits into a production deployment

This knowledge becomes critical while troubleshooting production deployment failures.

---

# Production Scenario

Company

ABC Bank

A Platform Engineer modified a generated Helm Chart without understanding its structure.

During the production deployment:

- Ingress stopped working.
- HPA failed.
- ServiceAccount was removed accidentally.
- Rollback failed because templates were inconsistent.

After this incident, the engineering team made it mandatory for every DevOps Engineer to understand the generated Helm Chart before making changes.

We follow the same practice.

# Chart.yaml

```
Chart.yaml
```

Purpose

Contains chart metadata.

Example Information

- Chart Name
- Version
- Description
- API Version
- Application Version

Think of it as the identity card of the Helm Chart.

---

# values.yaml

```
values.yaml
```

Purpose

Stores configurable values.

Instead of hardcoding:

```
replicas = 3

image = api:v1

namespace = production
```

Helm reads these values from:

```
values.yaml
```

Every environment will have different values.

Example

Development

```
Replica = 1
```

Production

```
Replica = 5
```

Same template.

Different values.

---

# templates/

Contains Kubernetes resource templates.

Instead of static YAML files, these files contain Go Templates.

Helm converts these templates into Kubernetes manifests during deployment.

---

# deployment.yaml

Purpose

Creates Pods.

In our project

```
Frontend Deployment

API Gateway Deployment

Auth Deployment

Dashboard Deployment
```

Each application will eventually have its own deployment template.

---

# service.yaml

Purpose

Creates Kubernetes Service.

Allows communication between applications.

Example

```
Frontend

↓

API Gateway

↓

Auth Service
```

---

# ingress.yaml

Purpose

Creates Ingress resource.

Provides external access.

Example

```
Internet

↓

Ingress

↓

Frontend
```

---

# hpa.yaml

Purpose

Creates Horizontal Pod Autoscaler.

Production Example

```
CPU > 70%

↓

Increase Pods
```

This is why Helm generates an HPA template by default.

---

# serviceaccount.yaml

Purpose

Creates a Kubernetes ServiceAccount.

Applications use ServiceAccounts to communicate securely with the Kubernetes API.

Many enterprise applications require dedicated ServiceAccounts.

---

# _helpers.tpl

Purpose

Reusable template functions.

Instead of repeating labels everywhere,

Engineers define helper functions once.

Example

```
Common Labels

↓

Helper Template

↓

Deployment

↓

Service

↓

Ingress
```

This reduces duplication.

---

# NOTES.txt

Purpose

Displayed after successful installation.

Example

```
Application Installed

Access using

kubectl port-forward
```

Many enterprise teams customize NOTES.txt with operational instructions.

---

# tests/

Purpose

Contains Helm test Pods.

Used to verify whether the application was deployed successfully.

Production CI/CD pipelines often execute Helm tests after deployment.

---

# charts/

Purpose

Stores dependent charts.

Example

Application

↓

Redis Chart

↓

PostgreSQL Chart

↓

RabbitMQ Chart

Helm supports dependency management.

# Production Best Practices

- Never delete generated templates without understanding their purpose.
- Keep Chart.yaml clean.
- Store configuration only in values.yaml.
- Reuse helper templates.
- Keep templates generic.
- Use chart dependencies instead of copying YAML.
- Maintain one chart per application unless a shared chart strategy is justified.

---

# Common Mistakes

- Hardcoding values inside templates.
- Removing helpers.
- Deleting ServiceAccount unnecessarily.
- Ignoring NOTES.txt.
- Editing templates before understanding values.yaml.
- Copying templates between charts instead of reusing helpers.

# Interview Questions

## Q1. What is the purpose of Chart.yaml?

### Answer

Chart.yaml stores chart metadata such as name, version, description, API version and application version.

---

## Q2. Why does Helm generate values.yaml?

### Answer

values.yaml stores configurable values that are injected into templates during rendering, allowing the same chart to be used across multiple environments.

---

## Q3. Why is _helpers.tpl important?

### Answer

It contains reusable template functions that reduce duplication and standardize labels, names and annotations across Kubernetes resources.
